| 作成日 | 2026-07-26 |
| ステータス | 条件付き確定（§10 の確認完了後に確定） |
| 備考 | 料金・無料枠の確認日: 2026-07-27。導入時にも各サービスの公式ページ・利用規約を再確認すること |

---

## 1. 背景と課題

### 現状

| 項目 | 内容 |
|------|------|
| 構成 | 静的HTML / CSS の1ページ構成 |
| ホスティング | ロリポップ（2年契約・約30,000円） |
| ドメイン | ムームードメイン（継続使用） |
| 更新方法 | 開発者がHTMLを直接編集し、FTPでアップロード |
| ソース管理 | 別PC上のリポジトリ |

### 課題

1. **更新のたびに開発者の作業が必要**。店舗側が独力でメニューや休業日を変更できない
2. **サーバー費用が継続的に発生**する
3. **ZIPファイル手動・FTPアップロード**のため作業ミスのリスクがある
4. **PCが故障するとソースが失われる**可能性がある
5. 画像が未最適化、ファイル名に日本語が使われている

---

## 2. 前提となる非機能要件

技術選定は、以下の非機能要件から逆算して決定した。

| # | 要件 | 優先度 |
|---|------|--------|
| NFR-1 | 継続的な費用を極力ゼロに近づける | **1** |
| NFR-2 | 開発者にとって技術的な学習価値があること | 2 |
| NFR-3 | PC初心者が独力でコンテンツを更新できること | 3 |
| NFR-4 | 表示速度・検索エンジンでの評価を現状より向上させること | 4 |

### 補足: 優先度の根拠

- **NFR-1**: ロリポップの既払い費用は回収不能な費用として扱い、選定根拠にはしない。契約満了後に追加の固定費を発生させない方針
- **NFR-3**: 更新対象は「新着情報・休業日」「メニュー名と価格」「メニュー写真」「営業時間・店舗情報」の4領域
- **NFR-4**: 現状ですでにインデックスされている。ゼロからの立ち上げではなく改善が目的

| オンライン決済 | 上記が不要なため連鎖的に不要 |

**※ただし、後から追加できる構成にしておくことを選定条件に含める。**

## 5. 層ごとの選定根拠

### 5-1. フレームワーク: Astro + TypeScript

| 項目 | 内容 |
|------|------|
| 決定的な理由 | 静的生成がデフォルト。CMSのデータをビルド時に取り込むため、閲覧時にAPIを呼び出さない。 |
| 副次的な理由 | 既存のHTML / CSS をほぼそのまま移植できる。画像最適化とsitemap生成を利用でき、構造化データ（JSON-LD）はページ側で明示的に実装できる。 |
| 対応する要件 | NFR-1（microCMSの転送量を消費しない）、NFR-4（表示速度）、NFR-2（TypeScript標準） |

#### 却下した代替案

| 候補 | 却下理由 |
|------|----------|
| Next.js | 1ページ規模に対して機能が多く、React学習も同時に必要になる。今回必要な静的サイトとCMS連携にはAstroの方が小さく始められる。 |
| 素のHTML / CSSを維持 | CMS連携ができず、今回の主目的（NFR-3）が達成できない。 |
| Hugo / Eleventy | 静的サイトとしては成立するが、今回の学習対象をTypeScriptとAstroに絞るため採用しない。 |
| WordPressテーマ | 後述のCMS選定で却下したため連動して却下。 |

---

### 5-2. CMS: microCMS（Hobbyプラン）

| 項目 | 内容 |
|------|------|
| 決定的な理由 | 管理画面が日本語で、Hobbyでも最大3名・5 APIまで利用できる。PC初心者の更新候補として最有力。 |
| コスト根拠 | Hobbyプランは無料、クレジットカード登録不要。公式のプラン説明は「個人の小規模なプロジェクトに」としているため、店舗サイトでの利用可否は導入前に提供元へ確認する。 |
| 対応する要件 | NFR-3（最重要）、NFR-1 |

#### 制約と対応方針

| 制約 | 内容 | 対応 |
|------|------|------|
| API数 | 5個まで | 「新着情報」「メニュー」「店舗情報・営業時間」の3 APIで設計する。メニュー写真はメディアとしてメニューAPIから参照し、カテゴリはセレクトフィールドで持つ。 |
| データ転送量 | 月20GB。超過するとAPIが停止する | ビルド時に取得し、画像も静的アセットとして出力してCloudflareから配信する。CMS画像URLをそのまま`img`要素へ出力しない。閲覧者のアクセスは原則として消費しないが、ビルド時のAPI・画像取得は消費するため使用量を監視する。 |
| 権限管理 | Hobbyには無い | 編集者が1〜2名のため許容。 |

#### 導入条件

- Hobbyプランを店舗サイトに利用できることをmicroCMSに確認し、回答を記録する。確認できない場合はTeamプランまたは別CMSへ切り替える。
- CMSのAPIキーはCloudflareのビルド環境変数にのみ保存し、Git・ブラウザ配信ファイル・クライアント側のJavaScriptに含めない。
- 公開操作後はWebhookでビルドされるため、更新が表示されるまでにビルド時間を要する。更新担当者向けに「公開 → ビルド完了を確認 → 本番表示を確認」の手順を用意する。

#### 却下した代替案

| 候補 | 却下理由 |
|------|----------|
| WordPress | サーバー継続で有料（NFR-1に反する）。セキュリティ更新が開発者の永続的な負担になる。 |
| Decap CMS / Sveltia CMS | 無料だが、編集者にGitHubアカウントとログインが必要（NFR-3に反する）。 |
| Google スプレッドシート | 無料だが画像管理が弱く、公開設定のミスによる情報漏洩リスクがある。 |
| Contentful / Sanity | 管理画面が英語。NFR-3を満たさない。 |

---

### 5-3. ホスティング: Cloudflare Pages（Freeプラン）

| 項目 | 内容 |
|------|------|
| 決定的な理由 | 静的サイトのリクエストは無料・無制限で、Git連携による自動デプロイとCDN配信を利用できる。 |
| コスト根拠 | Freeは月500デプロイ、1プロジェクトあたり独自ドメイン100件、ファイル数20,000・1ファイル25 MiBまで。動的なPages FunctionsはWorkersの無料枠を消費する。 |
| 副次的な理由 | Git連携による自動デプロイ。CDN配信による表示速度改善。必要になればPages Functions（Workers）を追加できる。 |
| 対応する要件 | NFR-1（最重要）、NFR-4、NFR-2（CI/CD・DNS・CDNの学習） |

#### 却下した代替案

| 候補 | 却下理由 |
|------|----------|
| ロリポップ継続 | 有料（NFR-1に反する）。Git連携がなくFTPでの手動アップロードが残る。 |
| Vercel | **無料プランは事業目的の利用が規約違反。** 店舗サイトは営利となるためProプラン（月20ドル）が必要。開発体験は優れるが、NFR-1で失格。 |
| Netlify | 商用利用は可能だが、無料枠の転送量が月100GB上限。Cloudflareより狭い。 |
| Firebase Hosting | 無料枠の転送量が狭く、Git連携も一手間多い。 |

## 6. 検討したが採用しなかった上位構成

「月額を払えるならどうか」を比較のために検討した。

| 層 | 採用案 | 上位案 |
|----|--------|--------|
| CMS | microCMS Hobby（0円） | microCMS Team（4,900円） |
| ホスティング | Cloudflare Pages（0円） | Vercel Pro（USD 20/月・開発者1席〜） |

**追加費用**：microCMS Team は **4,900円/月〜（税別）**、Vercel Pro は **USD 20/月・開発者1席〜**。為替・税・追加利用料で変動するため、合計額を固定値では記載しない。

### 仕様変更で得られるもの

| 項目 | 差分 | 今回の評価 |
|------|------|-----------|
| Vercel Pro | 商用利用、Vercel機能群、利用量の上限拡張 | Astroの静的サイトには必須ではない |
| microCMS Team | API: 10個、転送量200GB、CSVエクスポート・APIグループ等 | 現在の3 API・少人数運用では必須ではない |
| microCMS Business | 権限管理 | 編集者ごとの権限制御が必要になった場合に再検討する |

**※結論: §10 の利用可否確認が取れるまでHobbyを前提に進める。確認不可、または権限管理が必要になった場合はCMSを再選定する。**

## 7. 将来の拡張余地

注文・予約機能を追加する場合の想定。  
**※現時点では実施しない。**

| 段階 | 内容 | 追加技術 | 追加費用 |
|------|------|----------|----------|
| Lv.1 | フォームで注文を受け、店舗に通知 | Cloudflare Pages Functions（Workers）+ メール送信手段 | 無料枠内を想定。メール送信サービスは別途費用が発生し得る |
| Lv.2 | 注文履歴を保存し、店舗が確認できる | 上記 + Cloudflare D1 + 管理画面の認証 | 無料枠内を想定 |
| Lv.3 | オンライン決済 | 上記 + Stripe | 決済手数料が発生 |

### 重要な点

- **Lv.1 / Lv.2 を追加してもAstro・microCMS・Cloudflare Pagesの構成は変更不要。** サイト本体は静的のまま、APIを追加するだけで済む。
- Lv.1から、スパム対策・入力値検証・個人情報の取扱いを設計する。Lv.2では、さらに店舗向け管理画面の認証・権限・データ保持期間・バックアップが必要になる。
- **Lv.2とLv.3の間に大きな段差がある。** 決済は手数料に加えて特定商取引法の表記、返金・キャンセル対応といった運用負荷が発生する。
- Workers Freeは1日10万リクエストかつCPU時間10 ms/リクエスト、D1 Freeは5 GBストレージ・1日500万行読み取り・1日10万行書き込み。想定規模では十分と見込むが、公開前にフォーム送信量とスパム対策を含めて見積もる。

## 8. この選定が崩れる条件

前提が変われば見直す。トリガーを明示しておく。

| 条件 | 見直す層 |
|------|----------|
| 月額数千円の予算が確保できる | ホスティング・CMSを上位案で再検討 |
| 店舗側が更新しない方針に変わる | CMSが不要になる。Astro単体で足りる |
| 更新対象のデータモデルが増え、5 APIでは不足する | CMSのAPI数・プランを再検討。ページ数ではなくコンテンツモデル数で判断する |
| CMSの画像URLを閲覧者へ直接配信する、またはビルド時の転送量が増える | microCMSの転送量20GBを再評価 |
| 編集者が3名を超える、または編集権限を分ける必要がある | CMSのメンバー数・権限管理を再検討 |
| microCMS Hobbyの店舗サイト利用を確認できない | CMSをTeamプランまたは別サービスへ再選定 |
| 注文・予約を実装する | 上記「将来の拡張余地」に従ってWorkers / D1を追加 |


## 9. 移行手順（概要）

| Step | 内容 | 本番への影響 |
|------|------|-------------|
| 0 | リポジトリをGitHubへ集約し、秘密情報を含めないことを確認。Google Search Console登録。メールの利用状況・DNSレコード・メールデータの移行要否を確認 | なし |
| 1 | ローカルでAstro環境を構築 | なし |
| 2 | 要件・仕様に沿って画面を実装（データはハードコード） | なし |
| 3 | Cloudflare Pagesへデプロイ（仮URL）。`X-Robots-Tag: noindex` を設定し、本番へは公開しない | なし |
| 4 | microCMSを3 API（新着情報 → メニュー → 店舗情報）に接続 | なし |
| 5 | Webhookを設定し、公開操作で自動デプロイされること、失敗時にロールバックできることを確認 | なし |
| 6 | 構造化データ・sitemap・画像最適化、title/description/canonicalを実装。旧サイトと本番候補のURL・HTTPステータスを比較 | なし |
| 7 | ネームサーバーをCloudflareへ変更。メール関連レコードとメールサービスを移行し、送受信テストを実施 | **※あり※** |
| 8 | Search Consoleで公開を確認後、ロリポップを契約満了時に解約 | あり |

### SEOに関する留意点

- **ドメイン・URL・主要コンテンツ・HTTPステータスを維持できれば、ホスティング移行だけでURLごとの301リダイレクトは不要。** ただし、クロール・表示速度・一時的な到達不能の影響はあり得るため、切替前後にSearch Consoleと主要URLを確認する。
- **Step 3の仮URL（`*.pages.dev`）には `X-Robots-Tag: noindex` を返す。** `robots.txt` のクロール禁止だけではURLが検索結果に出ることがあるため、noindexを明示する。
- URL構造を変更する場合は301リダイレクトが必要。ただし現状は1ページ構成のため、トップページURLを維持すれば問題は起きない。
- Step 6の前にDNSのTTLを短縮しておくと、切り戻しが速くなる。

### メールに関する留意点

ロリポップで独自ドメインのメールアドレス（`xxx@kiwamitakoyaki.com`）を使用している場合、ネームサーバー変更時にMXだけでなくSPF・DKIM・DMARCなどメール関連DNSレコードを引き継ぐ。ロリポップのメール機能を解約するなら、先に後継メールサービスを決め、既存メールの退避・メールボックス移行・送受信テストを完了する。

これを忘れるとメールが届かなくなる。Cloudflare Email Routingは受信メールの転送用途であり、同じ独自ドメインから送信するメールボックスの代替にはならない。
